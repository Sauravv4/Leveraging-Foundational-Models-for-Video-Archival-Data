Abstract 
This supporting report documents, in full technical depth, the design, implementation, verification, and 
critical appraisal of a study investigating how an open-source large language model can be adapted for 
structured information extraction from clinical doctor-patient dialogue. Conversational text is informal, 
multi-turn, and context-dependent, properties that extraction systems built for static documents do not 
handle well. A custom, human-reviewed, 798-example benchmark was constructed from the MTS-
Dialog corpus using Qwen3-8B as an annotator, with two competing automated quality-filtering 
strategies trialled before a full human review pass. Four research questions were then tested against this 
benchmark: whether LoRA fine-tuning outperforms zero- and few-shot prompting; whether explicit 
annotation guidelines embedded in the fine-tuning prompt improve generalisation to clinical specialties 
unseen during training; which of three structured output representations — JSON function-calling, 
natural-language labels, or Python dataclass instances — minimises hallucination; and how extraction 
performance degrades with conversational complexity and specialty unfamiliarity. Naive fine-tuning 
produced a null result relative to prompting; guideline-conditioned fine-tuning produced a modest but 
real improvement with reduced hallucination; JSON output decisively minimised hallucination against 
the alternatives; and a measurable but partly artefactual generalisation gap was observed between seen 
and unseen specialties. Beyond restating these results, this report additionally provides a mathematical 
formulation of the extraction and scoring task, a full account of the project's life cycle and verification 
methods, a justified inventory of every tool used, and an honest critical appraisal — including two 
worked case studies, a disclosed AI-use statement, and an evidence index linking every reported claim 
to its source artefact.

Chapter 1 — Introduction 
1.1 Context and the Extraction Problem 
Information extraction (IE) — the transformation of unstructured text into structured, machine-
actionable records — has traditionally assumed static, well-formed input: news articles, scientific 
abstracts, legal filings. Conversational data violates every one of these assumptions. Utterances are 
informal, incomplete, spread across multiple turns between speakers, and frequently rely on implicit 
context — a symptom mentioned three turns earlier, referenced only as “it”; a question asked and then 
answered with a bare “no”. This gap matters increasingly as organisations accumulate large volumes of 
conversational data — clinical encounters, customer-service transcripts, voice-assistant logs — that 
must be mined for structured, actionable content. A hospital needs a structured clinical summary from 
a doctor-patient dialogue; the same underlying extraction problem recurs, in different clothing, across 
every domain where humans talk rather than write. 
Large language models have demonstrated substantial zero-shot IE capability, but this capability is 
neither free nor uniform. GPT-3.5 achieves only 18.22 F1 on standard named-entity recognition without 
task-specific adaptation [3], and zero-shot dialogue-state tracking trails fine-tuned models by 10–20 
points on MultiWOZ [6], a benchmark built on the neural dialogue-systems paradigm established by 
earlier pretrained-language-model approaches [5]. Conversational IE further compounds these 
weaknesses: existing benchmarks evaluate entity, relation, intent, and event extraction largely in 
isolation, and none jointly assesses all of these within the same multi-turn conversational context. This 
project addresses that gap directly by evaluating LLM-based extraction on the highest-stakes 
conversational setting available within its scope — clinical dialogue — where extraction errors carry 
real consequences and where the tension between fine-tuning effort, prompt engineering, and 
hallucination control is most acute. 
1.2 Engineering Problem versus Scientific Problem 
It is useful to separate what this project had to build from what it set out to discover. The engineering 
problem is concrete: read a doctor-patient conversation, produce a structured extraction of its clinically 
relevant content, and score that extraction against a human-verified gold standard. This project 
implements that loop directly — an annotation pipeline, two competing quality-filtering strategies, a 
LoRA fine-tuning pipeline, and a three-format evaluation harness (Chapter 4) — and every stage 
produces an inspectable artefact (a JSON file, a CSV of scores, a saved adapter). 
The scientific problem is different, and is the one the four research questions actually target: whether 
small-scale parameter-efficient fine-tuning is worth its cost relative to prompting alone; whether a 
specific, low-cost intervention (embedding annotation guidelines in the fine-tuning prompt) measurably 
improves generalisation to specialties the model has never been fine-tuned on; which structured output 
representation should be the default choice under a hallucination-sensitive evaluation standard; and how 
much of an observed generalisation gap is a genuine model limitation versus an artefact of how the 
benchmark itself is scored. Building a working extraction pipeline was necessary to answer these 
questions, but it is not, on its own, the contribution — a pipeline that extracts structured facts without 
establishing whether its adaptation strategy generalises, or whether its apparent gains survive a fair 
comparison against a strong baseline, would not answer any of them. 
1.3 Research Question, Aim and Objectives 
The aim of this project is to determine how an open-source LLM can be reliably adapted — through 
fine-tuning, prompt design, and output-format selection — to extract structured clinical facts from 

doctor-patient conversation, and to characterise the conditions under which each adaptation strategy 
succeeds or fails. Four objectives follow, each mapped directly to one research question addressed in 
Chapter 6: 
Establish whether parameter-efficient LoRA fine-tuning improves on zero-/few-shot prompting alone, 
on a held-out specialty split (RQ1). 
Establish whether explicit annotation guidelines, embedded in the fine-tuning prompt, improve 
generalisation to specialties unseen during training (RQ2). 
Establish which of three structured-output representations — JSON function-calling, natural-language 
labels, or Python dataclass instances — best balances accuracy against hallucination (RQ3). 
Characterise how extraction quality degrades with conversational complexity and specialty familiarity, 
and how much of any observed gap is genuine versus a scoring artefact (RQ4). 
The expected contribution is threefold: a human-verified, difficulty- and specialty-stratified 
conversational IE benchmark for the clinical domain; a reusable evaluation harness scoring three 
distinct structured-output formats against a single set of gold labels; and an honest empirical account of 
where a small-scale, consumer-hardware LoRA fine-tuning pipeline does and does not outperform 
prompting — including a genuine null result, reported rather than concealed. 
1.4 Contributions and Claim Boundaries 
Several boundaries are stated here explicitly, in the interest of the same methodological honesty this 
report returns to throughout. This project makes no claim that its findings generalise beyond a single 
clinical domain; no claim of superiority over a proprietary model, since no GPT-3.5/4 comparison was 
run; no claim that its LoRA hyperparameters represent an optimum, since they were adopted from 
literature defaults rather than searched; and no claim that the resulting system is suitable for autonomous 
clinical documentation or decision-making — it is positioned strictly as a clinician-facing drafting aid 
requiring mandatory human review (Chapter 8). Following a supervisor-approved scope review, the 
project's original plan — spanning at least three domains, proprietary and literature-baseline 
comparisons, and five research questions — was formally narrowed to a single domain and four 
research questions (Chapter 7). These boundaries are the single largest limitation of the present work 
and are revisited critically in Chapter 8, stated here as a scope decision rather than left implicit.

2.2 On-Demand Information Extraction (ODIE) — Jiao et al., EMNLP 2023 [1] 
Approach. Jiao et al. introduce On-Demand Information Extraction: a user supplies a natural-language 
instruction describing what should be extracted, and the model returns the requested content as a 
structured table, rather than being locked to one fixed extraction schema. The authors construct the 
InstructIE dataset — 14,579 ChatGPT-generated training pairs spanning 61 domains, plus 150 human-
annotated test examples — and fine-tune LLaMA-7B with LoRA in two variants: ODIE-Direct, which 

emits the table immediately, and a chain-of-thought variant that reasons before emitting. Evaluation 
combines Soft-Match F1 (via SentenceBERT similarity, so paraphrases are not penalised as harshly as 
under exact-match F1), ROUGE-L, and human ratings. 
Merit. ODIE-Direct outperforms comparable open-source baselines by roughly 5% and nearly matches 
GPT-4 despite being two orders of magnitude smaller — a concrete existence proof that a small, LoRA-
adapted open model can approach proprietary-model performance on structured extraction from free 
text, which directly motivated this project's choice to attempt the same with Qwen3-8B rather than 
assuming a large proprietary model would be required. 
Weakness and gap. ODIE operates exclusively on static, single-author documents. Its six-step 
ChatGPT-based data-generation pipeline has no mechanism for multi-turn context: it does not resolve 
pronoun or ellipsis reference across turns, does not distinguish speakers, and has no notion of a fact 
being confirmed versus merely raised and then denied — exactly the properties that make doctor-patient 
dialogue harder than the news/Wikipedia-style text ODIE was evaluated on. 
How this project differs. ODIE's six-step data-generation pipeline is the direct template this project 
adapted for benchmark construction (Chapter 4), substituting Qwen3-8B for ChatGPT as the annotator 
and multi-turn doctor-patient transcripts for ODIE's static source documents. Where ODIE's automated 
filtering step is a single LLM pass, this project trialled two distinct filtering strategies before adding a 
full human review pass — a more rigorous quality-control chain, made necessary precisely because 
dialogue introduces the negation and misattribution failure modes that static-text extraction does not. 
2.3 Zero-Shot Dialogue State Tracking through Function Calling (FnCTOD) — Li et al., 
ACL 2024 [2] 
Approach. Li et al. reframe dialogue-state tracking as a function-calling problem: each dialogue domain 
is modelled as a distinct callable function, and the slot values the user has specified become that 
function's arguments, with the model emitting a JSON function call. A two-step decomposition — select 
the domain, then generate its arguments — shortens the prompt and improves accuracy. A version fine-
tuned on 7,200 dialogues across 36 domains (FnCTOD-LLaMA2-13B) matches ChatGPT's zero-shot 
DST performance and improves on GPT-4's average Joint Goal Accuracy by 14%. 
Merit. FnCTOD is the paper in this review set most directly situated in the conversational domain, and 
its function-calling framing gives a genuinely dialogue-native precedent for representing extracted state 
as a structured, machine-parseable call rather than free text — exactly the property this project's RQ3 
investigates for a different task. 
Weakness and gap. FnCTOD's schema is closed and fixed: each function's argument set is a small, 
enumerable slot vocabulary (cuisine type, price range, area). This suits task-oriented booking dialogue 
but cannot express open-ended free-text fields — a clinical diagnosis or a doctor's recommendation 
cannot be reduced to a small enumerable set of slot values without losing information. 
How this project differs. FnCTOD's JSON function-call framing is the direct ancestor of this project's 
JSON output condition in RQ3. The project's schema is deliberately hybrid: three list-valued fields 
(symptoms, family_history, medications) behave like FnCTOD's closed slots, while two fields 
(diagnosis, recommendation) are left as open free text — bridging FnCTOD's closed slot-value schema 
and ODIE's fully open table extraction. 

2.4 InstructUIE — Wang et al., arXiv 2023 [3] 
Approach. Wang et al. unify named-entity recognition, relation extraction, and event extraction under 
a single instruction-tuned FlanT5-11B model, jointly fine-tuned across 32 datasets. InstructUIE 
achieves 85.19% average NER F1 against an 80.09% BERT baseline, outperforms GPT-3.5 zero-shot 
on relation extraction, and generalises to seven NER domains never seen during its own fine-tuning. 
Merit. InstructUIE's seven-domain zero-shot generalisation experiment is the direct precedent for this 
project's seen/unseen specialty split and RQ4 generalisation analysis, demonstrating that instruction-
tuned models can be evaluated meaningfully on generalisation to excluded categories, not merely in-
distribution performance. 
Weakness and gap. InstructUIE reports strong aggregate accuracy but no hallucination metric and no 
comparison against a function-calling output representation — its own output format is natural-
language, label-based text. Nor does it address dialogue. 
How this project differs. InstructUIE's natural-language label output is the direct ancestor of this 
project's “NL” output condition in RQ3. This project's finding that the NL-label format hallucinates 
substantially more (33.8–58.0%) than a JSON function-calling alternative (7.5–9.7%) is a direct, 
empirical extension of the evaluation gap InstructUIE itself leaves open. 
2.5 GoLLIE — Sainz et al., ICLR 2024 [4] 
Approach. Sainz et al. argue that LLMs should be trained to follow explicit annotation guidelines, not 
just a bare task instruction. Guidelines are represented as Python dataclasses, with each field's docstring 
carrying its definition and a commented worked example. Five regularisation techniques — class-order 
shuffling, class dropout, guideline paraphrasing, candidate-label sampling, and class-name masking — 
stop the model from memorising label names as shortcuts. GoLLIE 7B outperforms an 11B InstructUIE 
by 13 F1 points on zero-shot benchmarks and hallucinates in under 1% of its predictions. 
Merit. GoLLIE is the source of both the dataclass output format compared in RQ3 and the entire premise 
of RQ2. Its near-1% hallucination rate is direct evidence that hallucination is not solely a function of 
model size and can be engineered down. 
Weakness and gap. GoLLIE is evaluated only on static news and biomedical text, never on dialogue, 
so its central claim — that guideline-conditioning improves generalisation — had never been tested 
against conversational, informally phrased input before this project's RQ2. Its 13-point improvement 
also uses the full five-technique regularisation regime at 7B–34B scale on high-end hardware, a 
materially larger investment than a single-consumer-GPU MSc project can reproduce. 
How this project differs. RQ2 is a direct, deliberately simplified replication of GoLLIE's central claim 
in a setting GoLLIE never tested: conversational clinical dialogue, using a single technique (guideline 
text embedded in the fine-tuning prompt) rather than GoLLIE's full regularisation regime. The resulting 
+2.3-point gain is treated not as a failure to replicate, but as evidence — discussed in Chapter 6 — that 
GoLLIE's larger reported gain likely reflects its additional regularisation machinery rather than 
guideline text alone, a hypothesis this project's simpler ablation is well positioned to have surfaced 
precisely because it isolates guideline presence as the sole variable. 
2.6 Complementary Technical and Corpus Literature 
Beyond the four core methodological papers reviewed above, six further sources supply the technical 
and corpus foundations this project builds on directly. 

Parameter-efficient fine-tuning. LoRA [7] freezes a pretrained model’s weights entirely and injects 
small, trainable low-rank decomposition matrices into selected linear layers, reducing the number of 
trainable parameters by orders of magnitude relative to full fine-tuning while retaining most of its 
benefit — the technique underlying every fine-tuning run in this project (Chapter 4). QLoRA [8] 
extends this further with 4-bit NF4 quantisation of the frozen base weights, together with double 
quantisation and paged optimisers to control memory spikes during training. This is the specific 
combination of techniques that made fine-tuning an 8-billion-parameter model feasible at all on a single 
8 GB consumer laptop GPU: without QLoRA’s quantisation scheme, Qwen3-8B alone would not fit in 
the available VRAM budget, let alone leave room for gradients and optimiser state. 
Backbone model. The Qwen3 technical report [9] documents the architecture, training regime, and 
reported benchmark performance of the model family used throughout this project, for both the 8B 
backbone and the smaller 1.7B variant used in the supplementary model-size comparison (Section 6.8). 
Its reported strong instruction-following at the 7–8B parameter scale is the direct justification for 
selecting Qwen3-8B over a larger, less locally deployable alternative. 
Source corpus. MTS-Dialog [10] is the project’s source corpus: a publicly released collection of 
doctor-patient dialogue transcripts paired with human-written clinical summaries, built originally for 
clinical note-generation research. This project repurposes those human-written summaries in a role their 
original authors did not intend — as an independent cross-check during the self-verification quality-
filtering pass (Chapter 4) — extracting additional evidentiary value from an existing, already-curated 
resource rather than requiring separately collected ground truth. 
Task-oriented dialogue paradigm. Budzianowski and Vulic [5] and the MultiWOZ 2.2 paper [6] 
together establish the neural, pretrained-language-model paradigm for task-oriented dialogue systems 
and the benchmark that paradigm is most commonly evaluated against. They are not sources this 
project’s methodology is built on directly, but they supply the field-level context motivating its opening 
claim: that zero-shot dialogue-state tracking trails fine-tuned models by a substantial, well-documented 
margin on MultiWOZ, framing how large a fine-tuning-versus-prompting gap is typically expected to 
matter in dialogue tasks generally. They also represent the kind of standard, multi-domain dialogue 
benchmark this project’s original plan intended to incorporate before the scope was narrowed to a single 
clinical domain (Chapter 7).

2.8 Synthesis: Positioning and Novelty of the Present Work 
Read together, the four core papers reveal a research space explored along individual axes but never 
combined. ODIE and InstructUIE demonstrate that structured extraction and cross-domain 
generalisation are achievable with fine-tuned open models, but neither addresses dialogue. FnCTOD 
addresses dialogue directly and popularises function-calling as an output representation, but only within 
closed, fixed slot schemas. GoLLIE addresses guideline-conditioning and output-format hallucination 
control with the strongest results of the four, but only on static text. No existing work in this review 
combines fine-tuning-versus-prompting comparison, guideline conditioning, and output-format 
hallucination control within a single conversational, open-ended-field benchmark evaluated under 
identical conditions. This project's contribution is precisely that combination, instantiated in a single 
high-stakes domain, with RQ1 (informed by ODIE and FnCTOD), RQ2 (informed by GoLLIE), and 
RQ3 (informed by all three output-format papers) tested on identical held-out data so their effects can 
be compared directly against one another — something none of the four source papers' own, mutually 
non-comparable benchmarks permits. 
 
 

Chapter 3 — Problem Statement and Mathematical Formulation 
This chapter defines the extraction task, the three structured output representations compared in RQ3, 
and every scoring metric used throughout this report and the Research Paper, independent of any 
particular model or experimental run. All definitions below are taken directly from the project's own 
scoring implementation (common_extraction.py), so the equations reported here are the equations the 
reported numbers were actually computed with, not a post-hoc restatement. 
3.1 Task Definition 
Let c denote a conversation: an ordered sequence of turns c = (u1, u2, …, un), where each turn ui is 
attributed to either the doctor or the patient speaker role. Each conversation in the benchmark carries a 
gold annotation g, a structured record over five fields: symptoms (a list of {name, duration, severity} 
objects), family_history (a list of {relation, condition} objects), medications (a list of {name, dose, 
frequency} objects), diagnosis (free text), and recommendation (free text). A model under evaluation, 
given c and a format-specific prompt, produces a predicted record p over the same five fields. The 
extraction task is to produce p such that every fact in p is (i) present in c, (ii) correctly attributed to the 
patient rather than a third party, and (iii) not a fact the patient explicitly denied. 
3.2 Structured Output Representations 
Three surface representations of the same underlying record p are compared in RQ3, each with its own 
parser in common_extraction.py: 
JSON function-calling: p is emitted as a JSON object matching the five-field schema exactly, parsed 
by regex-extracting the first balanced {...} block from the model's raw output and validating it with 
json.loads. 
Natural-language (NL) labels: p is emitted as delimiter-separated labelled lines (e.g. “symptoms: 
headache (duration: two days, severity: severe); …”), parsed with a purpose-built delimiter parser 
rather than a general-purpose format. 
Python dataclass: p is emitted as a literal MedicalRecord(...) constructor call, parsed with a safe, non-
evaluating AST visitor that walks the parsed syntax tree and reads back field values without 
executing arbitrary code from model output. 
Structural validity for a given output o is a binary indicator: valid(o) = 1 if the format-specific parser 
returns a well-formed record, 0 (a parse failure) otherwise. Structural-validity rate over a set of N 
outputs is the mean of valid(o) across that set. 
3.3 Fuzzy Slot-Level F1 for List Fields 
For each list-valued field (symptoms, family_history, medications), predicted items and gold items are 
matched using token-Jaccard overlap rather than exact string equality, so a paraphrase (“kids” vs. 
“children”) still counts as a match. For two strings a and b, let A and B be their normalised (lower-
cased, punctuation-stripped) token sets. The fuzzy-match predicate is: 
fuzzy_match(a, b) = 1  if  |A ∩ B| / |A ∪ B|  ≥  0.5,  else 0.        (1) 
Matching proceeds greedily: each predicted item's key string (e.g. a symptom's name; a family-history 
item's “relation condition” concatenation) is compared in order against all not-yet-matched gold items, 
and the first fuzzy match found is consumed. Given true positives tp (matched pairs), precision = tp / 
|predicted|, recall = tp / |gold|, and the field's F1 is the harmonic mean: 
F1_field = 2 · precision · recall / (precision + recall).        (2) 

3.4 Token-Overlap F1 for Free-Text Fields 
The two free-text fields (diagnosis, recommendation) are scored with standard precision/recall over 
normalised token sets, rather than the greedy item-matching used for list fields, since each is a single 
string rather than a list of discrete facts: precision is the fraction of predicted tokens that also appear in 
the gold text, recall is the fraction of gold tokens that also appear in the predicted text, and F1 is again 
their harmonic mean (Equation 2). By convention, two empty strings score F1 = 1.0 (correctly 
predicting “nothing stated”), while one empty and one non-empty string score F1 = 0.0. 
3.5 Macro-F1 
The headline comparison metric used throughout this project is macro-F1: the unweighted arithmetic 
mean of the five per-field F1 scores for a given item, then averaged again across all items in the 
evaluated set: 
macro-F1 = (F1_symptoms + F1_family + F1_meds + F1_diagnosis + F1_recommendation) / 5.  (3) 
Macro-F1 (rather than a token-count-weighted average) was chosen specifically so that a field with 
typically shorter content, such as medications, is not swamped in the aggregate score by a field with 
typically longer content, such as symptoms — each of the five clinical fact types is treated as equally 
important to get right. 
3.6 Hallucination Rate 
Hallucination rate is defined as the fraction of predicted facts whose normalised tokens do not appear 
anywhere in the source conversation's normalised token set. For a prediction p with extracted facts F = 
{f1, …, fk} (every symptom name, family-history condition, medication name, plus the diagnosis and 
recommendation strings, when non-empty), and conversation token set C: 
hallucination_rate(p, c) = |{ f ∈ F : tokens(f) ∩ C = ∅ }| / |F|.        (4) 
This is a grounding proxy, not a clinical-correctness check: a fact can be grounded (its tokens appear in 
the conversation) while still being wrongly attributed or negated, which is why hallucination rate is 
reported alongside, never instead of, macro-F1 throughout this project. 
3.7 Constraints and Evaluation Objective 
The evaluation objective is not simply to maximise macro-F1. It is to select an adaptation strategy — 
prompting, fine-tuning, or fine-tuning with guidelines — and an output format whose macro-F1, 
hallucination rate, and structural validity are jointly acceptable, and to characterise, rather than hide, 
how that joint acceptability changes between specialties seen during any fine-tuning and specialties 
held out entirely (RQ4). The mathematical formulation therefore keeps macro-F1, hallucination rate, 
and structural validity as three separate reported quantities rather than collapsing them into one scalar, 
so that a format or condition which trades one for another (as RQ3's few-shot interaction with 
hallucination shows, Chapter 6) remains visible rather than averaged away.

4.2 Annotation Prompt Design 
Every benchmark item begins as a raw conversation passed to Qwen3-8B with an extraction prompt 
engineered specifically to handle two recurring error types identified during early trial runs. The prompt 
requires the model to attend to who each fact belongs to — the symptoms field is reserved strictly for 
the patient's own current experience, never a family member's — and to negation: a symptom the doctor 
asks about and the patient denies must not appear anywhere in the output. The operative rules, taken 
directly from the deployed prompt, read: 
“The 'symptoms' field is ONLY for things the patient THEMSELVES is currently experiencing... Do not 
put a family member's condition, history, or behavior in 'symptoms' — even if it sounds like a symptom... 
The doctor often asks about a symptom and the patient DENIES it... A denied/negated symptom means 
the patient does NOT have it — do NOT include it.” 
This exhibit is quoted directly from ANNOTATION_PROMPT in the project's own annotation 
notebook, reproduced here as evidence that the negation- and attribution-handling described throughout 
this report is a real, deployed constraint on the annotator, not a post-hoc description of desired 
behaviour.

4.4 Quality-Filtering Architecture 
Two automated filtering strategies were implemented and trialled before human review, as shown in 
Figure 2. The first, an NLI-based consistency check, converted each extracted fact into a natural-
language claim (e.g. “The patient currently has {symptom}.”) and tested it against the conversation 
using cross-encoder/nli-deberta-v3-base, flagging a fact when the classifier returned “contradiction” 
above 0.5 confidence or “neutral” above 0.7 confidence. Run across all 800 items, this flagged 717 of 
1,687 facts (42.5%) — on manual inspection, a substantial share of these were in fact correct, indicating 
the classifier, trained on single-sentence premise/hypothesis pairs, generalised poorly to long, multi-
turn medical dialogue where a fact stated early can be clarified or confirmed many turns later. 
The second strategy, adopted in its place, uses Qwen3-8B itself as a verifier: for each item, every 
extracted fact is listed and the model is asked to mark each TRUE or FALSE strictly against the 
conversation, with explicit instructions to mark FALSE any fact that is unmentioned, explicitly denied, 
or misattributed to the wrong person. This flagged 275 of 1,687 facts (16.3%) — a more plausible rate 
on the same manual-inspection standard — and every flagged fact was then reviewed by hand, corrected 
where necessary (most commonly negation errors and one misattribution case), and merged back into 
the final benchmark. 

4.5 Model Architecture and LoRA Configuration 
The backbone model is Qwen3-8B [9], an open-source instruction-tuned decoder-only transformer, 
selected for strong reported instruction-following at the 7–8B scale, open weights permitting full 
gradient access unavailable with a proprietary API, and mature LoRA/PEFT tooling. The model is 
loaded in 4-bit precision (NF4 quantisation with double quantisation, float16 compute) [8], the specific 
choice that made loading and fine-tuning an 8-billion-parameter model feasible within an 8 GB VRAM 
budget. A LoRA adapter [7] is attached to the four attention projection matrices (query, key, value, 
output) with rank 16, scaling alpha 32, and dropout 0.05, training 15,335,424 of 8,206,070,784 
parameters (0.187%) while leaving base weights frozen. Rank, alpha, and target-module selection 
follow established LoRA and GoLLIE defaults [4], [7] rather than a project-specific search, a trade-off 
discussed critically in Chapter 8. 
4.6 Training Procedure 
Training data for the RQ1 (no-guidelines) condition comprises 250 of the 709 seen examples, drawn 
with a fixed random seed (42) for reproducibility. Each training example pairs the extraction prompt 
with the gold JSON annotation as the target completion; prompt tokens are masked to label value −100 
during tokenisation, so cross-entropy loss is computed exclusively over the target JSON completion, 
not the input. Training uses a per-device batch size of 1 with gradient accumulation over 8 steps 
(effective batch size 8), a single epoch, learning rate 2e-4, fp16 mixed precision, the paged 8-bit Adam 
optimiser, and gradient checkpointing enabled throughout. For RQ2, an otherwise identical script 
substitutes the guideline-augmented prompt (Section 4.3) for the plain extraction prompt, holding every 
other hyperparameter fixed.

5.5 Threats to Validity, Stated Before Results 
Two classes of threat to validity are stated here, before any result is presented in Chapter 6, rather than 
discovered retrospectively by a reader comparing tables. 
Infrastructure threats 
torch.cuda.is_available() returning True is not sufficient evidence that GPU computation will succeed: 
one candidate environment reported CUDA availability while every real matrix multiplication crashed, 
because the installed PyTorch build lacked compiled kernels for the RTX 5060's Blackwell (sm_120) 
architecture. A second, separately maintained conda environment was found to hold a CPU-only 
PyTorch build with none of transformers, peft, bitsandbytes, or datasets installed, despite being 
recorded elsewhere as “working.” Both were caught by an explicit GPU matrix-multiplication smoke 
test before any experiment in this report was trusted to have actually run on GPU. 
Data and protocol threats 
A tokenisation-length threat was diagnosed during the RQ2 training run: the longer guideline-
augmented prompts caused 177 of 250 training examples (71%) to exceed the original 640-token cap, 
silently truncating — and in some cases entirely discarding — the target JSON completion. This was 
caught by auditing the tokenized length distribution directly and fixed by compacting the guideline text 
and raising the cap to 768 tokens, restoring the truncation rate to 8% (20/250), matching the original 
RQ1 run's rate on the same metric. A second threat concerns sample size: the RQ1/RQ2 headline 
comparisons rest on only 89 unseen items, and no formal significance test has yet been run on the 
observed deltas (Chapter 8); a 1–2-point macro-F1 difference on this sample should be read as 
suggestive, not conclusive, until that validation is performed. A third threat concerns correlated bias: 
the initial annotation and the self-verification quality-filtering pass (Chapter 4) both use the same 
Qwen3 model family, so a systematic bias in how that model perceives a given specialty's terminology 
could, in principle, be encoded into the gold labels themselves rather than caught by a genuinely 
independent check. The subsequent human review pass mitigates, but does not eliminate, this risk.

6.2 Worked Example 1: Negation Handling and Its Limits 
The following case study, drawn directly from the annotation pipeline's own recorded output for 
benchmark item ID 34, illustrates both the negation-handling rule working as intended and a residual 
limitation it did not fully resolve. 
Conversation (verbatim): 
DOCTOR: Have you lost weight? / PATIENT: No, I haven't, you can ask my daughter. / DOCTOR: 
How about anything like fever, nausea, vomiting, pain? / PATIENT: No. / DOCTOR: And as we 
discussed you have problem talking and comprehending. / PATIENT: Yes. / DOCTOR: And you get 
urine infections too? / PATIENT: Yes. / DOCTOR: And as discussed, your drainage is similar to past 
episodes when you had such infection? / PATIENT: Yes. 
Recorded annotation output: 
symptoms: [{"name": "difficulty talking and comprehending", "duration": "similar to past episodes", 
"severity": "not specified"}]; family_history: [{"relation": "daughter", "condition": "weight loss"}]; 
medications: []; diagnosis: ""; recommendation: "". 
The negation rule worked correctly in one respect: “weight loss” — explicitly denied by the patient 
(“No, I haven't”) — was correctly excluded from the symptoms field, where a naive extractor would 
otherwise have recorded it simply because the word appeared in the doctor's question. However, the 
annotation still shows a residual artefact: the denied weight loss was folded into family_history, 
attributed to “daughter,” apparently because the patient's aside (“you can ask my daughter”) was 
misread as introducing a fact about the daughter rather than merely offering a witness to confirm the 
patient's own denial. The annotation also misses two facts the patient explicitly confirmed — urine 
infections and drainage similar to past episodes — which do not appear anywhere in the recorded output. 
This example is included here, rather than a cleaner one, specifically because the project's own critical-

appraisal standard (Chapter 8) is to report evidence of residual error alongside evidence of success, 
rather than present only favourable cases.

6.10 Integrated Answer to the Research Questions 
Taken together, the evidence in this chapter answers each research question, but with boundaries that 
must be stated alongside the answer rather than after it. RQ1: naive LoRA fine-tuning on 250 examples 
does not outperform few-shot prompting on this benchmark — a negative result, not a null instrument, 
since the same pipeline detects a real, positive effect in RQ2 under an otherwise identical protocol. 
RQ2: embedding explicit annotation guidelines in the fine-tuning prompt produces a small but real, 
directionally consistent improvement in both accuracy and grounding, at effectively zero additional 
compute cost — the project's most actionable finding for a practitioner operating under a similarly 
constrained data and hardware budget. RQ3: JSON function-calling output should be the default 

structured-output choice for a hallucination-sensitive extraction task, unambiguously, on every metric 
measured. RQ4: extraction quality degrades meaningfully with conversational difficulty, and a real, if 
partly artefactual, generalisation gap exists between clinical specialties represented during fine-tuning 
and specialties held out entirely — a gap this project's manual error review, rather than the raw 
aggregate metric alone, was needed to characterise honestly. 
 
 

Chapter 7 — Project Lifecycle, Tools, Verification and Validation 
7.1 Research Lifecycle as Decisions 
The project began with a supervisor-approved project plan specifying an ambitious original scope: a 
conversational information-extraction benchmark spanning at least three domains (healthcare, customer 
support, e-commerce), comparison against proprietary baselines (GPT-3.5, GPT-4) and three literature 
baselines (InstructUIE, GoLLIE 7B, FnCTOD-LLaMA2-13B), and five research questions. Following 
a formal scope review with the supervisor, the plan's boundaries were explicitly narrowed: the domain 
was restricted to healthcare dialogue only, sourced from MTS-Dialog; the standard multi-domain 
comparison datasets (MultiWOZ 2.2, Schema-Guided Dialogue, IE INSTRUCTIONS) were dropped; 
no proprietary-model comparison was run, owing to the absence of an API budget; no literature-baseline 
reproduction was attempted, owing to the 8 GB GPU budget and the fact that two of the three literature 
baselines are themselves larger than Qwen3-8B; and a fifth research question (joint multi-format 
generalisation) was formally dropped, consistent with the plan's own risk-mitigation register, which 
permitted dropping RQ4/RQ5 once RQ1–RQ3 were judged solid. 
Development then proceeded through the benchmark-construction stage described in Chapter 4: 800 
conversations sampled and annotated, two competing filtering strategies trialled (one abandoned after 
inspection, the other adopted), a full human review pass, and a locked, stratified benchmark. Four 
parallel experimental tracks were then implemented against that locked benchmark — baseline 
evaluation, LoRA fine-tuning (RQ1, then RQ2), the three-format evaluation harness (RQ3), and the 
stratified RQ4 analysis — each producing a saved CSV of scores consumed unmodified by the final 
results-aggregation notebook. A hard submission deadline of 4 September 2026 was confirmed by the 
module supervisor, together with the requirement to prepare a Research Paper, this Supporting Report, 
a recorded presentation, and code as four separate final deliverables.

7.3 Verification and Provenance 
Verification was treated as an explicit step at three separate points in the life cycle, rather than a single 
end-of-project check. 
Data verification: raw LLM-generated annotations were verified twice, by two independent methods 
(NLI entailment, then LLM self-verification), before a full human review pass verified every fact 
either method flagged as uncertain — 275 flagged facts out of 1,687, rather than a full manual re-
annotation of all 1,687. 
Infrastructure verification: GPU computation was verified with an explicit matrix-multiplication smoke 
test rather than trusted from torch.cuda.is_available() alone, after this exact assumption was found 

false in one environment (Chapter 5). Token-length truncation was verified by auditing the 
tokenized length distribution of the RQ2 training set directly. 
Result verification: every headline figure reported in Chapter 6 and the Research Paper was re-derived 
directly from the project's saved CSV files by the results-aggregation notebook at the point of 
writing, rather than carried over by hand from an earlier draft. 
Cross-condition validation: RQ1 and RQ2 share an identical 250-example training subsample (fixed 
seed = 42), identical LoRA configuration, and identical training arguments, differing only in 
whether the prompt includes guideline text — a controlled ablation design chosen specifically so 
RQ2's result could be attributed to guideline presence alone. 
7.4 Reproducibility Lessons 
A stratified 60-item human-evaluation package (rating sheet with a 4-level rubric adapted from ODIE, 
a separately kept answer key, and a correlation-scoring script) was built specifically to validate the 
automatic fuzzy-F1 metric against independent human judgement. This step was not completed at the 
time of writing and is reported here as an open limitation rather than omitted silently — a decision 
consistent with this report's wider policy of naming an incomplete or failed step explicitly rather than 
letting a tidy narrative erase it. The main reproducibility lesson carried forward is to make failure states 
first-class: the abandoned NLI-filtering run and its 717-fact flag list remain on disk rather than deleted, 
the RQ2 truncation bug's before/after token-length distributions remain available, and the incomplete 
human-evaluation package's built infrastructure (rating sheet, rubric, scoring script) is reported as built-
but-unused rather than not mentioned. 
7.5 Interactive Verification: The Live Extraction Demo 
Beyond the results-aggregation notebook (Section 7.3), the project also provides a live, interactive 
verification surface: gradio_demo.py, a browser-based application built on the Gradio framework 
(Section 7.2, Table 14). The demo loads the RQ2 guideline-fine-tuned adapter after merging it into the 
Qwen3-8B base weights via merge_lora_adapter.py, and lets a reviewer select any of the 798 
benchmark conversations by clinical section category, run extraction against it, and watch the model's 
structured output stream token-by-token as it is generated, rather than only as a finished block. On 
completion, the demo scores the output with common_extraction.py — the identical scoring module 
that produced every headline figure in Chapter 6 — computing per-field F1 against the conversation's 
gold annotation and its hallucination rate. 
This closes the loop between the static tables reported above and a reproducible, inspectable instance 
of the same pipeline: a reviewer can verify, on demand, that the reported RQ2 metrics correspond to 
real model behaviour on genuine benchmark items rather than to the aggregation notebook's output 
alone. Figure 9 shows the interface after extracting a family-history conversation (benchmark item 9): 
the model's live-streamed output, the parsed JSON extraction, and the resulting per-field F1 and 
hallucination-rate scores against the benchmark's own gold answer. A screen recording of this demo in 
live operation forms part of the video presentation submitted alongside the Research Paper and this 
Supporting Report.

Chapter 8 — Critical Appraisal, Ethics and AI Disclosure 
8.1 What Worked and What Underperformed 
The strongest parts of this project are the separation of evidence layers, the explicit comparison between 
an abandoned and an adopted quality-filtering method (rather than presenting only the method that was 
kept), the decisive and literature-confirming RQ3 result, and the honest reporting of RQ1's null result. 
The 798-example benchmark is genuinely human-verified, not purely LLM-generated: every fact 
flagged by either filtering pass was reviewed and, where necessary, corrected by hand. The RQ2 adapter 
was also successfully fused into the base model's weights, producing a complete, standalone model that 
loads and runs inference directly with no separate PEFT adapter required at inference time — a working, 
runnable artefact of the project's fine-tuning work. 
The underperforming part is fine-tuning itself, relative to what the project plan anticipated. RQ1's near-
zero gain over zero-shot prompting, and its shortfall against few-shot prompting, means the compute 
and engineering investment in the base fine-tuning pipeline did not pay off in isolation — it took the 

additional, low-cost guideline-conditioning intervention in RQ2 to produce a real, positive result. Scale-
down in scope also cost the project its originally intended competitive framing: with no proprietary or 
literature-baseline comparison, every result in this project is Qwen-internal, and the human-evaluation 
validation package, though fully built, was not completed in time to validate the automatic metric it was 
designed to check. 
8.2 Hindsight and Validity 
With hindsight, three process changes would likely have strengthened this project most. First, 
environment and infrastructure verification (GPU compute, tokenisation limits) should have been built 
as an automated pre-flight check run before every experiment, rather than discovered reactively after a 
run failed or silently misbehaved — both incidents in Chapter 5 were caught by manual inspection 
prompted by suspicion, not by a standing check that would catch a similar issue automatically next 
time. Second, even a lightweight 2–3-point hyperparameter sensitivity check, short of a full search, 
would have let RQ1's null result be interpreted with more confidence as a genuine ceiling effect rather 
than a possible artefact of under-training. Third, the human-evaluation package should have been 
scheduled earlier in the project timeline, budgeted as its own milestone with dedicated time set aside, 
rather than treated as a final step to complete once every other experiment was finished — a sequencing 
choice that is the direct reason it remains incomplete. 
On validity specifically: internal validity is improved, but not fully resolved, by the controlled 
RQ1/RQ2 ablation design and the complete-container-style seen/unseen split constructed before any 
fine-tuning run. Construct validity is limited by the fuzzy-F1 metric's own design choices (Chapter 3) 
— a metric built to be lenient toward paraphrase is also, by construction, somewhat more forgiving of 
genuine near-misses, a trade-off made deliberately but worth naming. External validity is bounded by 
a single clinical corpus and a single backbone model family; nothing in this report should be read as a 
claim about LLM-based extraction in general. 
8.3 Responsible AI, Fairness and Environmental Limits 
Bias. The benchmark's sub-specialty distribution is imbalanced (Table 4, Chapter 5): general medicine 
accounts for 33.3% of examples, while the least-represented specialties (oncology, urology) each 
account for around 2%. Any model evaluated against this benchmark is therefore assessed — and, if 
trained on similarly distributed data, will perform — unevenly across specialties. This is compounded 
by the fact that the initial annotation and self-verification steps share the same underlying model family: 
a systematic bias in how that model perceives a given specialty's terminology risks being encoded into 
the gold labels themselves, rather than caught by a genuinely independent check. 
Privacy. The MTS-Dialog corpus is a publicly released research dataset not drawn from identifiable 
real patient encounters. Any future deployment of this project's pipeline on real clinical transcripts 
would require dedicated de-identification, regulatory compliance, and institutional ethical approval, 
none of which is in scope for, or satisfied by, this academic project. 
Fairness. RQ4's measured seen-versus-unseen performance gap is directly a fairness concern if any 
system built on this methodology were deployed operationally: patients whose conversations fall into 
an under-represented or entirely unseen specialty would systematically receive lower-quality automated 
extraction than patients in well-represented specialties, with no indication to the clinician unless the 
system's confidence or specialty coverage is surfaced explicitly. 
Transparency. Hallucination rate is reported as a first-class metric throughout this project, not a 
secondary diagnostic, precisely because a syntactically well-formed structured output — particularly in 
the JSON and dataclass formats — can appear trustworthy while containing fabricated content. Even 

the best-performing format still hallucinates 7.5–9.7% of extracted facts; this residual rate is reported 
explicitly rather than obscured behind an aggregate accuracy figure. 
Accountability and human oversight. Given the hallucination rates and the seen/unseen generalisation 
gap documented in Chapter 6, this project's explicit position is that the resulting model and pipeline are 
appropriate only as a clinician-facing drafting aid, with mandatory human review before any extracted 
fact enters a patient record or informs a clinical decision. No claim is made, or should be inferred, that 
this system is suitable for autonomous clinical documentation or decision-making without a human 
clinician in the loop. 
Environmental limits. All experiments were run on a single local 8 GB laptop GPU rather than a shared 
cluster, and every training run's duration (approximately 42 minutes for RQ1, 109 minutes for RQ2) is 
reported in Chapter 5 for transparency. No comparative energy-use claim is made, since exact power 
draw was not instrumented; this is named as a limitation rather than estimated.

Chapter 9 — Conclusion and Future Work 
9.1 Conclusion 
This report has documented, in full technical depth, a study of how an open-source large language 
model can be adapted for structured extraction from clinical conversation. A 798-example, human-
reviewed, difficulty- and specialty-stratified benchmark was constructed from the MTS-Dialog corpus 
using a two-stage quality-filtering process — one strategy trialled and abandoned, one adopted — 
followed by full human review. Against this benchmark, four research questions were tested under a 

mathematically formalised, identical scoring standard (Chapter 3). Naive LoRA fine-tuning on 250 
examples produced a null result relative to prompting; embedding explicit annotation guidelines in the 
fine-tuning prompt produced a modest, real, positive result at negligible additional cost; JSON function-
calling output decisively minimised hallucination against natural-language and Python-dataclass 
alternatives on every metric measured; and a measurable but partly artefactual generalisation gap was 
found between clinical specialties represented during fine-tuning and specialties held out entirely. 
The project's single largest limitation is scope: a single clinical domain, no proprietary or literature-
baseline comparison, and an unsearched hyperparameter space together mean these findings should be 
read as domain- and configuration-specific rather than general claims about LoRA fine-tuning, 
guideline-conditioning, or output-format design. Within that scope, the project delivers what it set out 
to: a reusable benchmark and evaluation harness, an honest empirical account — including a genuine 
null result reported rather than concealed — and a set of concrete, falsifiable directions for the work 
this project's own compute and time budget did not permit completing. 
9.2 Future Work 
Statistical validation: compute bootstrap confidence intervals or a paired significance test over the 89-
item unseen split for the RQ1 and RQ2 comparisons, to establish whether the observed deltas 
exceed sampling noise. 
Hyperparameter and data-scale ablation: systematically vary training-set size beyond 250 examples and 
epoch count, to test the leading hypothesis that RQ1's null result reflects under-training rather than 
a genuine ceiling effect. 
Multi-domain extension: extend the benchmark-construction pipeline (Chapter 4) to customer-support 
and e-commerce dialogue, restoring the original plan's multi-domain scope and testing whether 
RQ1–RQ4's findings replicate outside the clinical domain. 
Proprietary and literature baselines: run at least a partial GPT-4 zero-shot comparison on the 89-item 
unseen split, and either reproduce or cite comparable published numbers for InstructUIE, GoLLIE 
7B, and FnCTOD-LLaMA2-13B. 
Complete the human-evaluation package: finish rating the stratified 60-item sample and compute 
Pearson/Spearman/Kendall correlation against the automatic fuzzy-F1 metric, to validate — or 
correct — the metric design used throughout this project. 
Fuller GoLLIE-style regularisation for RQ2: test whether class-order shuffling, class dropout, and 
guideline paraphrasing close the gap between this project's +2.3-point result and GoLLIE's own 
+13-point result, isolating how much of that gap is attributable to regularisation technique versus 
data and compute scale. 
Mechanistic investigation of RQ3's few-shot/hallucination interaction: run controlled experiments 
varying output-format constraint independently of example count, to establish whether the effect 
observed in Section 6.6 is a general property of in-context examples or specific to less-constrained 
output grammars. 
Two questions raised by this work remain genuinely open. First, whether RQ1's null result reflects a 
fixable data/compute constraint or a real ceiling effect in strongly instruction-tuned models cannot be 
distinguished without the data-scale ablation proposed above. Second, the precise mechanism behind 
RQ3's few-shot-increases-hallucination effect for less-constrained output formats was not established 
within this project's scope. These directions extend the evidence rather than rewrite it; the RQ1 null 
result, the RQ4 generalisation gap, and the RQ3 output-format effect remain the three findings most 
worth carrying into any next iteration of this work.
